# 手机缩放性能排查（2026-10-31）

本轮完成了可复用的诊断、云端同次运行的近景→远景→返回近景检查，以及手机地图阴影负载优化。没有 iPhone 14 Pro 真机帧率和渲染计时数据，尚不能认定“常用视距稳定 60 FPS、返回近景恢复”已经达标，也不能认定用户遇到的是 GPU 瓶颈或浏览器帧率限制。

## 测量口径

- Babylon.js 固定为 9.32.1。浏览器为云端 Chromium，ANGLE SwiftShader 软件 GPU；手机布局 393×852 CSS 像素、DPR 3，实际渲染 589×1278。已有 DPR 上限 1.5 保持不变。
- 基线是在 `5d0f39d` 上加入同一套原生统计、尚未启用本轮阴影优化时取得。每轮在同一个页面内依次把正交视距设为 6、18、6，待镜头稳定，再运行至少 8 帧采样和截图。所有记录都使用成熟作物场景；最终测试显式等待小麦成熟，避免把生长产生的模板缓存误判为缩放泄漏。
- 帧间隔、P95 和 CPU 提交时间分别记录。`EngineInstrumentation` 提供可用时的原生 GPU 查询；不支持或尚无有效查询时为 `null`，另附 GPU 样本观测年龄。不能把 CPU 13 ms 解释成 GPU 13 ms，也不能简单把两个计时相加当作帧耗时。
- `SceneInstrumentation` 记录绘制次数、剔除 CPU 和渲染目标 CPU；当前唯一渲染目标是阴影。实际提交三角形使用 `scene.getActiveIndices()/3`，包括实例及阴影通道；不是所有可见标记网格的静态面数之和。阴影绘制次数、面数在原生阴影渲染回调前后取差。
- 同时记录实际分辨率、阴影大小、主相机每个人物的 LOD、资源数量、渲染循环数量和暂停状态。历史保存最近 120 个采样；后台恢复后帧统计重新开始，设置暂停期间的样本另行标记。
- 表中为各阶段最后一个稳定样本。居民仍自主运动，主通道面数和绘制次数会随遮挡、位置改变；不同运行的毫秒数也受软件 GPU 与宿主负载影响，因此以提交工作量验证优化，不将云端 FPS 外推到手机。

## 已核对的引擎能力与实现

1. 使用原生 `EngineInstrumentation` / `SceneInstrumentation`；显式引入 Babylon 模块化构建所需的 timeQuery/query 扩展。GPU 不可用时保留空值。
2. 保留原生主相机视锥剔除、人物屏幕覆盖率 LOD、已有树木/作物实例化和静态场景合批，不新增模型或修改原始素材。
3. 使用 `RenderTargetTexture.cameraForLOD`，让手机地图 1024 阴影通道复用已有地图级人物几何。主通道仍按实际视距选择精度；人物查看模式恢复主相机 LOD、2048 阴影和完整细节。
4. 核对 9.32.1 的 `Rendering/objectRenderer.js::_prepareRenderingManager`：显式 `renderList` 路径只检查启用、可见及层掩码，没有主相机视锥测试。因此只补充静态投影体过滤，通过原生 `getCustomRenderList` 和 `BoundingInfo.isInFrustum` 接入；不替换渲染器。物体本体或沿固定日光方向投到地面的包围体可能进入视野时均保留，避免裁掉画面外投进来的阴影。骨骼和形变网格保留原生路径；世界矩阵变化后更新缓存。该过滤按当前固定太阳方向、地面不低于 -0.2 的场景成立；未来变更日光或地形高度时需同步调整。
5. 保留原有 PCF 柔化、日光、材质、配色、动作和交互。没有依据不足的自动降分辨率，也没有新增渲染循环。

| 近景 6 | 310→285 | 4,504,076→2,686,728 | 180→168 | 2,751,618→997,238 |
| 远景 18 | 383→383 | 2,755,340→2,708,264 | 180→180 | 1,312,374→1,265,298 |
| 返回近景 6 | 324→275 | 4,705,478→2,741,560 | 180→168 | 2,751,618→997,238 |

近景与返回近景的阴影提交面数减少 **63.8%**；远景减少 **3.6%**。观察到的总提交面数减少约 40.3%、1.7%、41.7%，其中主通道存在居民位置差异，不能把总差值全部归因于优化。远景一次绘制包含的实例减少，不一定减少绘制次数。

| --- | ---: | ---: | ---: | ---: |
| 近景 | 24.4→7.5 | 2050.1→1363.3 | 1965.8→1466.1 | 2.6→2.2 |
| 远景 | 6.0→5.7 | 1238.3→1132.6 | 1284.4→1264.5 | 1.2→1.3 |
| 返回近景 | 7.0→5.4 | 2330.9→1224.0 | 2312.3→1172.6 | 3.1→1.4 |

这是软件 GPU 的约 0.4～0.9 FPS，不是 iPhone 性能。GPU 是最近有效异步样本，可能对应前一帧；软件 GPU 单帧超过 500 ms，统计窗口常只有一帧，P95 与该帧间隔相同，不应解读为长时间尾延迟。

优化后三段采样的 mesh / geometry / texture / material / skeleton / AnimationGroup 分别始终为 **424 / 394 / 13 / 167 / 14 / 19**，基线也相同；渲染循环始终 **1**。主相机六个人物的 141 个 LOD 部件在近景全部为原精度、远景全部切换地图精度、回近景全部恢复原精度。渲染分辨率和地图阴影大小保持 **589×1278 / 1024**。返回近景后阴影面数恢复为 997,238，低于远景 1,265,298，没有保留远景额外的静态阴影负载；总面数会因恢复近景高精度人物而增加，不能要求它必然低于远景。

本轮未发现缩放造成资源持续增加、重复渲染循环或 LOD 卡在远景状态。原生主通道已有剔除和 LOD，基线远景的面数甚至低于近景；这组结果没有复现用户描述的 iPhone 帧率行为。阶段原始数值见 [采样 JSON](zoom-samples-2026-10-31.json)。

## iPhone 上的复测方法

在同一次前台运行中，先用常用近景运行约 10 秒，再打开设置，点击“记录当前视距”；关闭设置，缩小到远景运行约 10 秒，再记录；返回原近景运行约 10 秒，第三次记录，最后点击“复制诊断信息”。记录按钮使用打开设置前最近一个未暂停样本，避免把设置暂停当成实际游戏负载。

反馈时附浏览器名称/版本、iOS 版本、低电量模式状态和设备是否明显发热。后续 04:04 UTC 的加载反馈已确认 iOS 26.2、微信内置浏览器 8.0.75、393×754 CSS 像素和 DPR 3；该记录尚未进入游戏，低电量/温度及实际渲染数据仍未确认，见 [加载反馈](../diagnostics/wechat-engine-loading-2026-10-31.md)。诊断包含浏览器标识、GPU 查询是否可用及样本年龄；普通游戏画面只保留简洁的 FPS/CPU 显示。

若返回近景后资源数量、渲染循环或 LOD 没有恢复，应先检查相应生命周期/状态；若负载和 GPU 耗时降低但帧间隔仍固定在约 33 ms，再在相同设备、浏览器、供电与温度条件下对照浏览器调度/帧率档位。Safari 可能不暴露 GPU 查询，空值不能证明 GPU 空闲。当前云端检查只能说明这次运行的渲染状态恢复，不能解释用户那次 iPhone 30 FPS 的根因。
