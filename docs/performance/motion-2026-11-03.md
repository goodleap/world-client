# 60 FPS 下的移动顿挫修复

用户在第一批上线后提供 M3 Pro / Chrome 的实测日志：平均 60 FPS、帧间隔约 16.67 ms、CPU 约 5～6 ms、没有慢帧，但人物移动明显顿挫。

代码确认了两个原因：位置和朝向每 50 ms 随固定逻辑步直接跳变，渲染帧之间没有插值；原来的 `animationTimeScale` 又用“本帧完成的逻辑时间 / 渲染时间”驱动骨骼，因此多数 60 Hz 帧的动作时间为零，之后集中推进。帧率计数稳定不代表人物每帧都在移动。

## 修改

- 保留 50 ms 固定逻辑步及三档相同的玩法时间。人物、狗和骑乘整体的位置与朝向在前后两个已完成的逻辑状态之间插值；不向未知的未来位置外推。
- 使用一个原生 TransformNode 父层提供视觉变换。逻辑根节点的位置不被插值覆盖，寻路、碰撞、任务、攻击和存档仍读取原始状态。名称、脚圈和路径起点跟随实际显示位置。
- 行走、跑步、作业等 Babylon 原生骨骼组按实际渲染时间连续播放。权威攻击姿态、灰狼运动/动作和箭矢按同样的逻辑步余量平滑采样；命中与资源结算频率不变。
- 暂停保留同一插值比例及骨骼姿态，恢复排除后台时间。新单位和读取存档时重置表现历史，避免从旧出生点滑入。
- 日志 `performance.latest.context.motion` 记录逻辑步长、该渲染帧完成的逻辑步数、插值比例、移动单位数、显示位置有变化的数量和动作时钟。今后可以区分“画面有帧但人物没推进”与实际掉帧。

插值最多落后逻辑一个固定步（50 ms），是避免穿过障碍和到达目的地后回拉的取舍；不会推迟攻击结算或改变存档位置。

## 验证

- 239 项逻辑测试通过，包含 60/30/20 渲染上限下完整玩法存档一致；新增测试用真实 Babylon TransformNode 验证逐帧平移、最短转向、非原点旋转、塔台高度、暂停和重载重置。
- `tools/review-motion.mjs` 使用真实 WebGL 模型，给游戏输入受控 1/60 秒时间并逐帧渲染。骑兵、农民、狗各采集 82 个持续移动帧：逻辑位置变化 28 次，而显示位置和骨骼姿态均变化 82 次。检查了连续帧截图，骑乘和名称跟随正常。
- 生产构建浏览器回归：桌面/手机日志和选中、暂停保持显示位置及骨骼、画质切换、保存重载；骑兵追击移动目标并命中；死亡停留、暂停、保存下沉阶段及奖励不重复。死亡用例把“观察阶段”和“点击暂停”放入同一个浏览器回合，消除云端跨调用期间错过阶段的竞态。

证据见 [motion-2026-11-03/](./motion-2026-11-03/)。云端验证证明每个渲染帧都有运动更新，不能代替 M3 Pro 或 iPhone 的实际帧率、温升和功耗测量。
